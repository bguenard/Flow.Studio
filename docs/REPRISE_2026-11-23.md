# Reprise du 23 novembre 2026 — diagnostic, modèle, backlog et incrément

Document de reprise du binôme architecte / designer. Il complète le `README.md` (fonctionnement) et ne contient aucune ligne de configuration client. État vérifié sur le code de ce dossier, le jeu fictif et le relevé local `work/wolf-real-snapshot.json` (16 parcours, 279 lignes voix).

Légende des statuts employés partout : **Réel** = lu dans Genesys ou dans le relevé · **Local** = calculé ou déclaré dans le Studio, conservé dans le navigateur · **Fictif** = jeu de démonstration · **À construire** = non implémenté.

Lecture Genesys Dublin (PKCE), import, inventaire v4/v5, graphe, édition en page, duplication complète, comparaison de deux parcours, copie sélective, journal de session. Les 91 tests passaient ; ils passent toujours.

### Limites de données et de fidélité relevées

- **Le relevé ne contient encore aucune évolution réelle** : pour l'adaptateur, les parcours génériques V1 et V2 sont identiques (0 écart). L'impact se démontre sur données réelles avec des brouillons locaux, ou sur le jeu fictif.
- **Parcours Gan Vie incomplet** : son entrée référence un calendrier absent du relevé v4. Le parcours s'arrête là ; rien n'est supposé au-delà (désormais signalé sur le parcours, sur sa carte et dans l'analyse).
- **Sous-traitements non suivis** : les colonnes de type de destination du relevé portent plus d'une centaine de sous-traitements `sub:` (qualification par bot, HNO, enregistrement, cibles SVI…). L'adaptateur les affiche comme contrôles mais ne suit pas leurs dépendances. Conséquence mesurée : **143 lignes voix sur 279 sont atteintes depuis une entrée** ; aucune ligne de `W_CHECK_*`, `W_RECORDING_V5`, `W_BLACK_LIST_v4`, `W_TECHNICAL_v4`, `W_TRF_FLOW_v4`, `W_RATIO_DISTRIB_v4`, `W_CALLBACK_v4` ne l'est. Le graphe sous-représente donc les parcours dont l'orientation passe par un sous-traitement. Une partie de ces lignes peut aussi être orpheline : non tranché.
- **Trois registres de types divergents** (`data-source.js`, `flow-clone.js`, `business.js`). Exemple : `validation`, `repeat`, `novalidation` (menus de consentement, présents dans le relevé) sont terminaux pour la duplication mais « non interprétés » pour le graphe.
- **Entrée v4 sans calendrier intégré** : la branche `OPEN` est libellée « Pendant l'ouverture » alors qu'elle sert de simple suite. Comportement non décrit dans la documentation fournie : à confirmer avec l'équipe WOLF avant de changer le libellé.
- **Ressources Genesys non résolues** (files, calendriers, prompts) : inchangé ; aucun horaire ni texte audio n'est inventé.

### Défauts UX prioritaires

1. Hiérarchie Core Model → versions → déclinaisons absente. **Traité.**
2. Rapprochement d'étapes fragile dès qu'une branche est redirigée (les deux équipes d'un menu devenaient « ambiguës » et produisaient de faux écarts). **Traité.**
3. Focus clavier perdu à chaque action (la page est re-rendue). **Traité.**
4. Libellés génériques de la source (quatre étapes nommées à l'identique, « CALENDRIER : »). À traiter par un libellé de substitution tiré de la branche d'arrivée, sans toucher aux valeurs.
5. Graphe : étiquettes posées sur les traits, convergences peu lisibles, hauteur fixe. À traiter.
6. Contrastes : les gris `#777`/`#888` des textes de 12–13 px passent sous 4,5:1 sur fond blanc. À corriger.

## 2. Modèle fonctionnel

```text
Core Model (famille nommée)                         ← déclaré
 ├─ Version 1 ── un parcours complet (entrée + étapes + embranchements)
 ├─ Version 2 ── un parcours complet            ← la dernière = référence en cours
 └─ Déclinaisons
      └─ Parcours d'entité (complet lui aussi)
           · version de référence déclarée (la « base »)
           · périmètre déclaré : non renseigné | activé | certains motifs | non activé
           · correspondance d'étapes référence ↔ entité (si connue)
           · origine : déclarée | créée dans le Studio | fictive
```

Règles de fond :

- **Tout rôle est une déclaration.** Ni le suffixe `V1/V2`, ni un marqueur dans une description, ni la présence d'une ligne ne créent une référence, une version adoptée ou un périmètre. Les parcours repérés par leurs marqueurs sont proposés « à classer », jamais classés d'office. Le libellé de version est une proposition modifiable.
- **Trois notions de version restent séparées** : moteur WOLF v4/v5 (lu), version du parcours de référence (déclarée), version adoptée par l'entité (déclarée).
- **Un parcours n'a qu'un rôle.** Une version qui sert de base à une déclinaison ne peut pas être retirée : la provenance ne disparaît pas en silence.
- **Analyse à trois états**, pour chaque réglage et chaque embranchement d'une étape rapprochée :

  | Référence en cours vs base | Entité vs base | Lecture |
  | --- | --- | --- |
  | changée | identique | Évolution de la référence à examiner |
  | identique | changée | Adaptation locale (ou valeur propre à l'entité si la référence prévoit un emplacement `[…]`) |
  | changée | changée, même valeur | Déjà aligné |
  | changée | changée, autre valeur | Conflit à arbitrer |
  | — | étape sans correspondance sûre | À rapprocher : aucun verdict |

- **Ce que l'analyse ne prouve pas** : qu'une version a été réellement adoptée, qu'un parcours est en service, qu'une entité est conforme. Elle lit trois parcours présents dans la source.

## 3. Architecture

| Couche | Modules | Rôle |
| --- | --- | --- |
| Source | `auth.js`, `genesys-direct.js`, `data-source.js` (import, `normalizeSnapshot`) | Lecture seule, snapshot gelé, colonnes inconnues conservées. |
| Représentation WOLF | `data-source.js` (`buildVoiceInventory`), `flow-clone.js` | Graphe v4/v5, duplication locale. |
| Modèle métier du parcours | `business.js`, `draft-fields.js` | Libellés, rubriques, comparaison et rapprochement d'étapes. |
| **Gouvernance** (nouveau) | `governance.js`, `governance-store.js` | Référentiel déclaré, analyse d'impact, persistance locale. Aucun DOM. |
| Interface | `app.js` (état, événements, pages historiques), `governance-views.js` (nouveau, vues pures), `ui-kit.js` | Rendu. |

Choix d'architecture de l'incrément :

- **Le référentiel est séparé du snapshot.** Il ne contient que des identifiants de parcours, des libellés et des périmètres ; jamais de ligne WOLF. Il peut donc être conservé (`localStorage`, clé `wolf-studio.governance.v1:local` ou `:demo`) et exporté sans embarquer de configuration client.
- **Identité des étapes** : une correspondance déclarée (`nodeMappings`, produite par la duplication ou fournie par le jeu fictif) prime sur toute heuristique. À défaut : entrée, lignes partagées, ensemble de chemins identique, chemin partagé non disputé, type unique. Deux candidats possibles ne sont jamais départagés par leur position.
- **Les déclinaisons créées dans la page ne sont pas enregistrées dans le référentiel durable** : leurs lignes disparaissent au rechargement, l'entrée deviendrait orpheline.
- **Une entrée dont le parcours est absent de la source courante est conservée**, pas réaffectée (changement de source, export partiel).
- Début de modularisation de `app.js` : blocs de page partagés déplacés dans `ui-kit.js`, nouvelles vues en fonctions pures. Pas de migration de framework : aucun bénéfice démontré à ce stade.

Limite structurelle connue, à traiter ensuite : **une « version » est aujourd'hui un parcours vivant dans les tables**. Si ses lignes sont modifiées dans Genesys, la base bouge sans que le Studio le sache. Une version immuable suppose de figer une empreinte à la déclaration et de signaler la dérive.

## 5. Incrément livré

« Du Core Model déclaré à l'impact d'une nouvelle version sur chaque entité. »

1. **Core Models** : familles déclarées (version en cours, déclinaisons, conflits), et parcours « à classer ».
2. **Rôle du parcours** : page de déclaration — référence (nouveau Core Model ou nouvelle version) ou déclinaison (version de base) ; retrait protégé.
3. **Page d'un Core Model** : versions avec leurs évolutions, puis pour chaque entité la version de référence, les écarts, l'impact de la version en cours et le périmètre déclaré.
4. **Impact d'une évolution** : trois colonnes (référence adoptée, référence en cours, entité), regroupées par nature — conflits, évolutions à examiner, adaptations locales, déjà alignés, valeurs propres à l'entité, étapes à rapprocher.
5. **Bandeau de rôle** sur chaque parcours ; avertissement quand le parcours est incomplet dans la source.
6. **Persistance locale du référentiel** ; référentiel inclus dans l'export des changements et visible dans le Diagnostic.
7. **Jeu fictif étendu** : une version 2 du Core Model (accueil, attente, priorité, délai, répétitions, repli du menu) pour montrer les quatre cas.
8. **Moteur de comparaison** : correspondances déclarées, rapprochement par chemin partagé, identifiant d'emplacement par écart.
9. **Clavier** : le focus est conservé après chaque action et placé sur le titre à chaque changement de page.

Vérifications : 106 tests (91 existants, 15 nouveaux sur la gouvernance et le rapprochement). Parcours navigateur rejoués en local sur le jeu fictif et sur le relevé réel importé : déclaration d'une famille à deux versions, rattachement des trois parcours d'entité, brouillons sur la version 2 et sur une entité, lecture de l'impact, rechargement et réimport (le référentiel revient). Nouvelles pages contrôlées à 1440 px et 820 px de large. **Non vérifié** : connexion Genesys en direct pendant cette reprise (le code de connexion n'a pas été modifié), affichage sur téléphone, lecteurs d'écran.

## 7. Backlog ordonné

**Gouvernance locale** (suite directe de l'incrément)

1. Décisions par écart — reprendre, conserver l'adaptation, reporter — avec auteur et justification ; application en brouillon pour les réglages copiables. « Décidé » et « appliqué » restent deux statuts.
2. Empreinte des versions déclarées et détection de dérive (version réellement immuable).
3. Rapprochement manuel des étapes ambiguës, enregistré dans les correspondances déclarées.
4. Persistance de session complète (IndexedDB) : brouillons, créations, journal ; export et réimport d'une session.
5. Pilotage transverse à tous les Core Models ; dérogations avec périmètre, responsable, échéance.

**Fidélité WOLF**

6. Un seul registre des types et tables (aujourd'hui trois copies qui divergent).
7. Sous-traitements `sub:` et tables de contrôle représentés comme étapes de contrôle rattachées.
8. Vue « configurations non rattachées à un parcours » pour les lignes jamais atteintes.
9. Libellé de la branche d'entrée v4 sans calendrier, après confirmation WOLF.
10. Rappel, répartition, transferts : validation sur les exports YAML réellement déployés.

**Expérience**

11. Impact reporté sur le graphe (étapes touchées, en conflit).
12. Libellés de substitution pour les titres génériques ou répétés.
13. Graphe : tracé des branches, convergences, grands parcours.
14. Contrastes, affichages étroits, lecteur d'écran.
15. Poursuite de la modularisation de `app.js` (état, routage, pages).

**Intégration distante** (après confirmation des contrats Genesys/WOLF et du périmètre d'autorisation)

16. Résolution des ressources Genesys (noms de files, calendriers, prompts) — suppose des droits de lecture supplémentaires.
17. Contrat d'écriture, BFF, droits par entité, audit durable, retour arrière.
18. Assistance IA sur un diff structuré, avec contrôle déterministe.
